# Excel Reconciliation & QA System

A Python application that reconciles two recurring Excel exports - orders and payments -
into a review-ready workbook: matched records, every class of discrepancy, and the input
rows that could not be used at all.

> **Synthetic portfolio project.** All data in this repository is generated by the
> bundled script (`scripts/generate_sample_data.py`). It is not client work, contains no
> real customer information, and the figures quoted below come from the committed sample
> dataset.

## 1. Project Overview

Reconciling an orders export against a payments export is a routine finance-operations
task that is usually done by hand: sort both files, look up each order, check the amount,
check the currency, notice the order that was paid twice. This project automates that
work end to end and produces a workbook a reviewer can act on, while keeping every
discrepancy traceable back to the worksheet row it came from.

The emphasis is on the parts that are easy to get wrong in production: input data
quality, transparent handling of unmatched records, cumulative exception reporting, and
numbers that can be explained.

## 2. Business Problem

Two exports arrive from different systems and rarely agree:

* an order is in the orders file but has no payment;
* a payment references an order that does not exist;
* amounts differ by a cent, or by a hundred euros;
* the payment is in a different currency than the order;
* a cancelled order was paid successfully, or a completed order's payment failed;
* the same order row or the same payment transaction appears twice;
* a row carries a null, an unparseable date, a malformed identifier or an unexpected
  status, so it cannot be reconciled at all.

Doing this manually is slow and, worse, it is easy to *silently* drop the rows that do
not match the expected shape - which is exactly where the real problems hide.

## 3. What the System Does

1. Loads the two Excel exports and records, for every row, its original worksheet row
   number.
2. Fails fast if an export is unusable (unreadable file, no header row, missing required
   column) instead of producing a report that hides the problem.
3. Normalizes values: trims text, upper-cases the agreed categorical fields, strips
   currency formatting, coerces dates.
4. Quarantines rows that are still unusable, with the reason and the offending value.
5. Matches the remaining rows on `order_id`, aggregating split payments per order.
6. Classifies every discrepancy - cumulative, so one order can raise several exceptions.
7. Detects duplicate order rows and duplicate payment transactions independently.
8. Computes the headline metrics and writes a ten-tab Excel workbook.

## 4. Architecture / Workflow

```
orders_export.xlsx   payments_export.xlsx
        |                     |
        v                     v
  1. load           excel_io      raw frames + source_row
  2. validate       validation    fatal: header + required columns
  3. normalize      normalize     trim / case / amounts / dates
  4. validate rows  validation    quarantine + valid frames
  5. match          matching      payments aggregated per order_id
  6. reconcile      matching      amount / currency / status checks
  7. classify       models        ExceptionType labels, cumulative findings
  8. summarize      metrics       SummaryMetrics
  9. report         report        outputs/reconciliation_report.xlsx
```

Each stage is a separate module with one job, and each one passes plain DataFrames on to
the next. `recon/pipeline.py` sequences the stages; `run.py` is the command line front
end. Only `excel_io`, `scripts/generate_sample_data.py` and `run.py` touch the
filesystem, and only `excel_io` touches Excel.

## 5. Reconciliation Rules

The primary key is `order_id`. Matching is **order-centric with payment aggregation**,
because one order can legitimately be paid in instalments:

* payments are grouped by `order_id` and summed, so three instalments of 40 against a
  120 order match;
* an order with no valid payment is a **Missing Payment**;
* `abs(order_amount - total_paid) > amount_tolerance` (default `0.01`) is an
  **Amount Mismatch** - a difference exactly equal to the tolerance still matches;
* any payment in a different currency than its order is a **Currency Mismatch**;
* any payment status that is not allowed for the order status is a **Status
  Inconsistency**, driven by `allowed_payment_statuses_by_order_status` in
  `recon/config.py`;
* a payment whose `order_id` appears nowhere in the orders export is a **Missing Order**;
* a payment whose order row exists but failed input validation is *not* a missing order -
  it is reported as an input data-quality finding, because the payment cannot be
  reconciled until the order row is fixed;
* duplicates are detected independently of matching (see below).

**Duplicates.** Duplicate order rows are listed in full with `duplicate_group_size` and
`is_primary`; only the first row per `order_id` takes part in matching, so one order gets
one verdict. Duplicate payments are found by repeated `payment_id`, then by a repeated
transaction fingerprint (`order_id`, `payment_date`, `payment_amount`, `currency`,
`payment_method`) under a different `payment_id`. **Duplicate payments stay inside the
order's paid total** - they are flagged, not removed - so a double charge shows up as both
a duplicate and an amount mismatch, which is what a reviewer needs to see.

**Cumulative exceptions.** Exceptions are not forced into one category per record. One
order can appear on the Amount Mismatches, Currency Mismatches and Status Inconsistencies
tabs at once, and `All Exceptions` holds one row per (record, exception type).

## 6. Data Quality Rules

Validation has two levels, deliberately kept apart.

**File level (fatal, exit code 2).** An unreadable file, an empty/missing header row, or a
missing required column stops the run before anything is written. A report built on a
missing key column would be meaningless, so the tool refuses rather than guesses. Extra
columns are logged as a warning and ignored.

**Row level (quarantine).** After normalization, any row with a problem is copied to the
`QA Issues` tab with `source_file`, `source_row` (1-based worksheet row), `qa_reason`,
`qa_details` and its original data. Quarantined rows are excluded from matching but are
never dropped: they also appear in `All Exceptions` as `Input Data Quality Error`.

| Reason | Meaning |
|---|---|
| `missing_required_value` | a required cell is empty |
| `invalid_date` | a date cell could not be parsed |
| `invalid_numeric` | an amount cell could not be read as a number |
| `malformed_id` | `order_id` / `payment_id` does not match the configured pattern |
| `unexpected_category` | value outside the configured currency / status / channel / method set |
| `non_positive_amount` | amount is zero or negative |

When one row has several problems, `qa_reason` reports the most serious one
(missing, then invalid date, invalid numeric, malformed id, unexpected category,
non-positive amount) and `qa_details` lists every finding on that row.

## 7. Exception Types

| Exception | Reported when |
|---|---|
| Missing Payment | Order has no valid payment transaction. |
| Missing Order | Payment references an `order_id` that does not exist in the orders export. |
| Amount Mismatch | Order amount and total paid amount differ by more than the tolerance. |
| Duplicate Order | Same `order_id` appears more than once in the orders export. |
| Duplicate Payment | Same `payment_id`, or an identical payment transaction, appears more than once. |
| Currency Mismatch | Payment currency differs from the currency of its order. |
| Status Inconsistency | Payment status is not a valid combination for the order status. |
| Input Data Quality Error | Row failed input validation, or a payment could not be reconciled because its order row did. |

## 8. Metrics and Definitions

| Metric | Definition |
|---|---|
| `total_orders` / `total_payments` | Rows read from each export, **before** quarantine |
| `matched_count` | Valid orders with zero failed reconciliation checks |
| `exception_count` | **Distinct records** with at least one reconciliation exception |
| per-type counts | Findings per exception type; a record can appear in more than one, so these **overlap** and can sum higher than `exception_count` |
| `reconciliation_rate` | `matched_count / total_orders` (`0.0` when no orders were read) |
| `quarantined_rows` (the plan's `qa_issue_count`) | Input rows set aside by validation, reported **separately** from reconciliation exceptions |

`exception_count` is deliberately never computed by adding the per-type counts together.
Input data-quality findings are excluded from `exception_count` (they are input problems,
not reconciliation differences) but are included in the per-type table so it always
matches the `All Exceptions` tab.

## 11. Usage

```bash
python run.py                                   # data/*.xlsx -> outputs/reconciliation_report.xlsx
python run.py --generate-sample                 # rebuild the sample exports first, then reconcile
python run.py --tolerance 0.05 --log-level DEBUG
python run.py --orders my_orders.xlsx --payments my_payments.xlsx --output outputs/custom.xlsx
```

| Flag | Meaning |
|---|---|
| `--orders PATH` / `--payments PATH` | Input exports (default: `data/orders_export.xlsx`, `data/payments_export.xlsx`) |
| `--output PATH` | Report path (default: `outputs/reconciliation_report.xlsx`) |
| `--tolerance 0.01` | Absolute amount tolerance in the order currency |
| `--seed 42` | Seed for `--generate-sample`, also recorded on the Summary tab |
| `--log-level INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR` or `CRITICAL` |
| `--generate-sample` | Build the deterministic sample exports before reconciling them |

Path arguments are resolved relative to the project root, so the command behaves the same
from any working directory.

| Exit code | Meaning |
|---|---|
| `0` | Success - the workbook was written |
| `2` | Fatal input/validation error - logged at ERROR, concise message on stderr, **no report written** |
| `1` | Unexpected error - stack trace logged, concise message on stderr |

## 12. Sample Data Generation

```bash
python scripts/generate_sample_data.py --order-count 7500 --seed 42
python run.py --generate-sample --seed 42     # same thing, then reconciles it
```

The generator is fully deterministic for a given seed and writes
`data/generation_manifest.json` alongside the exports, recording exactly which anomalies
were injected and which records they touched. The default sample contains 7,500 orders
(plus 25 duplicated order rows) and 7,994 payment rows across 18 months, four currencies,
five sales channels and four payment methods. Identifiers are obviously synthetic
(`ORD-000001`, `PAY-0000001`).

### Injected anomalies vs. reported findings

Some injected anomalies cascade, and the cascade is intentional:

| Finding | Injected | Reported | Why the numbers differ |
|---|---:|---:|---|
| Missing payments | 120 | 160 | +40: a quarantined payment leaves its order with no valid payment |
| Missing orders | 60 | 65 | +5: order rows whose `order_id` was corrupted by a malformed-id injection |
| Amount mismatches | 90 | 130 | +40: duplicate payments stay inside the paid total |
| Currency mismatches | 50 | 50 | - |
| Status inconsistencies | 45 | 45 | - |
| Duplicate order findings | 25 | 25 | - |
| Duplicate payment findings | 40 | 40 | 25 repeated `payment_id` + 15 repeated transactions |
| Quarantined rows | 80 | 80 | 20 missing value, 15 invalid date, 10 invalid numeric, 10 malformed id, 25 unexpected category |
| Input quality findings | 80 | 115 | +35: payments whose order row failed validation |
| Matched orders | - | 7,075 | 7,525 order rows read, 94.02% reconciliation rate |

## 15. Design Decisions

* **Aggregated, order-centric matching.** Grouping payments per order avoids false
  amount-mismatch noise on legitimately split payments.
* **Duplicates stay in the totals.** Removing them would silently change the amount a
  reviewer is checking; flagging them surfaces the double charge *and* the resulting
  imbalance.
* **Missing required columns are fatal.** A partial report is worse than no report.
* **Row-level quarantine instead of deletion.** Bad input rows are reported with their
  source row and reason, and excluded from matching.
* **Cumulative exceptions.** One record can fail several checks; each stays visible on its
  own tab and in the union.
* **QA issues are reported separately.** Data-quality findings are their own exception
  type and are excluded from the reconciliation exception count.
* **Source-row traceability.** Every exception row carries `source_file` and `source_row`,
  so any finding can be checked against the original worksheet.
* **Empty cells and `N/A` stay distinguishable.** Exports are read with
  `keep_default_na=False`, so an empty required cell is a missing value while a literal
  `"N/A"` is an invalid numeric value.
* **Locale-ambiguous amounts are flagged, not guessed.** Only conventionally grouped
  thousands separators are removed; `1.000,50` is reported as invalid rather than
  silently misread as `1.0005`.
* **Dates are parsed per value** (`format="mixed"`), because real exports mix date-only and
  datetime text in one column.
* **Categorical comparisons are case-insensitive**, so configuration values and normalized
  data cannot disagree about capitalization.
* **The generation seed is read from the manifest** and only recorded when the manifest
  describes the export being reconciled.

## 16. Limitations / Out of Scope

* Synthetic data only; there is no connection to a real ERP, payment provider or database.
* Excel input only (`.xlsx`, first worksheet of each file), no CSV or API ingestion.
* No currency conversion. Amounts are only compared within the same currency; a different
  payment currency is reported rather than converted at an FX rate.
* No fuzzy matching of near-miss identifiers: `ORD-0001` and `ORD-00001` are different.
* Duplicate detection flags the extra rows but cannot know which record is authoritative -
  that judgement stays with the reviewer.
* Duplicate order rows are excluded from matching (first row wins); they are reported, not
  reconciled.
* Amounts are compared with an absolute tolerance only; there is no relative-tolerance
  option.
* Scheduling, dashboards, PDF export and multi-user access are out of scope by design.
